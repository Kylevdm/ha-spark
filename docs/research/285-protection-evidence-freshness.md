# Protection evidence freshness for v1

Date: 2026-10-12

Ticket: [Research: trustworthy freshness for EV, dispatch, and battery-direction evidence](https://github.com/Kylevdm/ha-spark/issues/285)

Scope: planning evidence for the [accepted protection contract](https://github.com/Kylevdm/ha-spark/blob/b6d67bb/docs/adr/0007-protection-evidence-and-outage-boundary.md); no household telemetry or device writes.

## Finding

An HA state timestamp proves an HA publication, **not** an upstream device sample. `last_updated` changes only when value or attributes change; `last_reported` changes on every state write, even an identical one ([HA state-object documentation](https://www.home-assistant.io/docs/configuration/state_object/), [HA developer announcement](https://developers.home-assistant.io/blog/2024/03/20/state_reported_timestamp/)). Neither by itself proves that a cloud service refreshed its underlying device data. An integration's independently tracked *successful retrieval* time is stronger, but still dates the API response rather than a device measurement unless the API supplies a device sample timestamp.

The v1 rule should therefore use a **source capability gate**: an entity is protection-grade only after its exact integration version, polling configuration, publication path, and failure behavior have been checked. A successful post-startup observation is required; a restored HA value is never a first report. The age below is measured from the last **verified source retrieval or successful register read**, not from `last_changed` or an unqualified `last_reported`. `unknown`, `unavailable`, missing/future timestamps, failed reads, or an unproven cache are unknown evidence immediately, even before the age ceiling.

## Source findings and proposed limits

| Source | What the source establishes | Proposed maximum age and gate |
| --- | --- | --- |
| myenergi zappi status / plug / charging power | The [CJNE integration coordinator](https://github.com/CJNE/ha-myenergi/blob/ce5aca11dfe87b1644d73962d38d5797a21bcde4/custom_components/myenergi/__init__.py) polls by default every **60 s**, with configurable `scan_interval`; it calls `client.refresh()` and then history retrieval, raising `UpdateFailed` on exceptions. The [status and plug entities](https://github.com/CJNE/ha-myenergi/blob/ce5aca11dfe87b1644d73962d38d5797a21bcde4/custom_components/myenergi/sensor.py) expose client fields, without a device-sample time. The [HA unavailable rule](https://developers.home-assistant.io/docs/core/integration-quality-scale/rules/entity-unavailable/) describes coordinator failure behavior, but this does not prove cloud sample renewal. | **180 s** at the default 60 s polling, or `3 × configured scan_interval` for a slower installation, *only after* verifying a completed successful refresh can be distinguished from cached publications and that status and power came from the same refresh. If no such marker or upstream sequence/time can be demonstrated, status alone is **not protection-grade** for fresh clear reports; require a direct verified poll adapter or another source. Three periods allow two delayed polls while bounding a lost source. This is a design limit, not a vendor guarantee. |
| BottlecapDave Octopus HA dispatch entity | The [dispatch coordinator](https://github.com/BottlecapDave/HomeAssistant-OctopusEnergy/blob/7089181e7fd6b4801778e83c09691b30da9a44c5/custom_components/octopus_energy/coordinators/intelligent_dispatches.py) checks every **60 s**, but the API refresh interval is **3 min** ([constants](https://github.com/BottlecapDave/HomeAssistant-OctopusEnergy/blob/7089181e7fd6b4801778e83c09691b30da9a44c5/custom_components/octopus_energy/const.py)). It retains old dispatches after API failure. In manual polling mode the automatic coordinator returns stored data. The [binary entity](https://github.com/BottlecapDave/HomeAssistant-OctopusEnergy/blob/7089181e7fd6b4801778e83c09691b30da9a44c5/custom_components/octopus_energy/intelligent/dispatching.py) also restores its last state at startup and recomputes `on/off` against current time from stored dispatches. Thus its state, attributes, `last_updated`, and `last_reported` can advance without a new API response. The [per-device diagnostic entity](https://github.com/BottlecapDave/HomeAssistant-OctopusEnergy/blob/7089181e7fd6b4801778e83c09691b30da9a44c5/custom_components/octopus_energy/diagnostics_entities/intelligent_dispatches_data_last_retrieved.py) exposes `last_retrieved`, attempts and last error; [integration docs](https://bottlecapdave.github.io/HomeAssistant-OctopusEnergy/entities/intelligent/) explicitly point users to it. | **9 min** from the *matching device's* `intelligent_dispatches_data_last_retrieved` time, plus a successful post-restart retrieval, in automatic 3 min mode. Require diagnostic `last_error` absent and a matched dispatch payload/diagnostic read; age alone cannot accept a failed fetch that retained old slots. Manual polling is ineligible unless the owner configures a verified <=3 min refresh schedule within the integration's [20/hour limit](https://bottlecapdave.github.io/HomeAssistant-OctopusEnergy/services/) and proves success. Nine minutes is three planned refreshes and an explicit design bound. The binary entity alone is ineligible. |
| Direct Octopus Kraken `plannedDispatches` read | ha-spark's [query and fetch path](https://github.com/Kylevdm/ha-spark/blob/b8fdf9e/ha_spark/energy/octopus.py) reads `startDt`, `endDt`, `delta`, and source; it has no response-generation or device-sample timestamp. A successful request can establish when this application retrieved a schedule, and each interval has its own end; it cannot prove when Kraken last changed it. | **9 min** from a successful, validated API response if polled at <=3 min; do not carry the result through a failed call as fresh. Treat it as *schedule evidence*, not proof that the EV actually draws power. Retain a confirmed dispatch only to its last trusted `endDt`. If a shorter/longer polling interval is selected, make the bound `3 × interval`, capped at 9 min for v1. This is an application policy requiring an observed poll, not a provider freshness guarantee. |
| Battery charge/discharge direction, local inverter | The [reference preset](https://github.com/Kylevdm/ha-spark/blob/b8fdf9e/ha_spark/presets.py) configures a battery-power entity, but its entity name alone does not identify its integration, poll group, sign convention, or register. A candidate local Solis path, [SolaX Modbus](https://github.com/wills106/homeassistant-solax-modbus/blob/a58121681289db8b1cef7669f3ed395d70415c1b/custom_components/solax_modbus/const.py), defaults to **15 s**, with separately configurable fast/medium intervals ([config flow](https://github.com/wills106/homeassistant-solax-modbus/blob/a58121681289db8b1cef7669f3ed395d70415c1b/custom_components/solax_modbus/config_flow.py)). Its [poll implementation](https://github.com/wills106/homeassistant-solax-modbus/blob/a58121681289db8b1cef7669f3ed395d70415c1b/custom_components/solax_modbus/__init__.py) tracks `fresh_keys` per register block, illustrating why an unrelated entity write or group poll cannot renew battery evidence. | For a **verified local register source**, `min(3 × actual battery-register poll interval, 60 s)`, measured from a successful read of the battery register and its sign normalization; e.g. **45 s** at 15 s. A slower configuration that cannot meet the 60 s cap is not eligible for the overnight direction exception until separately justified. For cloud, derived, or unidentified entities, **no defensible numerical limit yet**: mark direction unknown and disable that exception until the producing integration and upstream sample time are established. |

These thresholds are proposed specification limits, not measured guarantees. The source implementations demonstrate nominal cadence and cache behavior; they do **not** establish myenergi cloud freshness, reference-household integration identity, or on-site latency. Those require a read-only commissioning trace. Version changes require rechecking the gate.

## State transitions to specify and test

The [accepted ADR](https://github.com/Kylevdm/ha-spark/blob/b6d67bb/docs/adr/0007-protection-evidence-and-outage-boundary.md) fixes the control response. Freshness classification applies before using any positive or negative value:

| Observation | EV hold | Dispatch hold | Overnight exception |
| --- | --- | --- | --- |
| Fresh positive | Enter or retain confirmed hold when status/power semantics confirm drawing. | Enter only for a fresh known active interval; retain its trusted end. | Active window still needs fresh non-discharging direction. |
| Positive value but stale/unproven sample | Starts no hold; an already confirmed EV hold remains. | Starts no new hold and cannot extend last trusted end. | Unknown direction blocks the exception. |
| Fresh negative | Count one independent successful EV clear report. Release only after **five consecutive fresh clear reports** and restoration verification. | No new hold. A previously trusted interval remains bounded by its own end; fresh schedule changes need validation. | Fresh non-discharging result may qualify with a verified charge window. |
| Negative value but stale/unproven sample | Does not count toward the five clears or release a confirmed hold. | Does not cancel or extend trusted interval. | Does not qualify. |
| `unknown`, `unavailable`, failed or absent read | Starts no hold; retains confirmed EV hold and raises degraded status. | Starts no new hold; last trusted end is the hard stop. | Does not qualify. |
| Recovery | Require a **new successful post-recovery source retrieval**. Restart the clear count at zero; no restored/cached report counts. | Accept newly retrieved schedule only after matching source validation; do not resurrect an expired hold. | Require a new successful battery read after recovery. |

“Five reports” must mean five distinct successful upstream refreshes, not five HA REST reads or five identical coordinator publications. At the default myenergi cadence that is at least about five minutes; at a slower configured interval it takes longer. Source-independent repeated reads of the same HA state cannot satisfy it. Dispatch `on/off` is a time-derived view and does not establish EV power; the [integration documentation](https://bottlecapdave.github.io/HomeAssistant-OctopusEnergy/entities/intelligent/) also says the binary sensor excludes bump charge and depends on its planned/started mode.

## Read-only commissioning proof required before enabling protection

1. Record the installed integration versions, configured poll intervals and exact producer for each selected entity. Observe a controlled sequence of unchanged values across at least five successful polls, then an HA restart and an upstream outage. Capture source success marker, source value, top-level HA timestamps and `unknown`/`unavailable` transitions with UTC times. No credentials or household IDs belong in the artifact.
2. For myenergi, prove `client.refresh()` completion corresponds to new status/power data rather than server cache, or add a source-owned sample/sequence marker. Confirm whether history-fetch failures make the whole coordinator unavailable after an otherwise successful live refresh. Confirm status and charging power are coherent enough to count as one clear sample.
3. For Octopus, pair the device diagnostic `last_retrieved`, `last_error`, dispatch list and binary state through unchanged polls, failed API calls, manual mode and HA restart. Verify that restored `off` and time-derived `on/off` never pass as new upstream data. For direct Kraken reads, record request completion and schedule end, and confirm no old response is reused after failure.
4. For battery direction, identify the actual register/API and sign convention. On a safe observation-only bench, compare a known charge, discharge, and idle transition with the reported value and per-register successful poll marker. Test an unrelated group poll and failed battery read; neither may renew the lease. Establish device clock/sample timestamp if cloud-mediated.
5. Run the state matrix above with a controllable clock, including restart between reports, five fresh clear reports, stale positive/negative, diagnostic error, future timestamp, and recovery. A source without the proof above remains disabled for the affected protection decision; alert the owner with the precise missing capability.

The existing ha-spark [HA state model](https://github.com/Kylevdm/ha-spark/blob/b8fdf9e/ha_spark/ha/models.py) can parse `last_reported`, but [current dispatch reads](https://github.com/Kylevdm/ha-spark/blob/b8fdf9e/ha_spark/energy/sources.py) do not yet enforce this source-specific contract. This note is planning evidence only.
