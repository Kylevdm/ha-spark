# Research: MCP SDK v2, URL elicitation, and ingress deep links for proposal approval

Issue: [Research: MCP SDK v2, URL elicitation, and ingress deep links for proposal approval](https://github.com/Kylevdm/ha-spark/issues/315), part of map [#247](https://github.com/Kylevdm/ha-spark/issues/247). Date: 2026-10-14.

Inputs: [Research: trusted in-conversation approval](https://github.com/Kylevdm/ha-spark/issues/268#issuecomment-6111196558) (URL elicitation is an *optional enhancement* over the propose-only contract) and [Agent config approval: who counts as the owner](https://github.com/Kylevdm/ha-spark/issues/278#issuecomment-6133071314) (an owner approves the stored **config proposal** on ingress; approve = commit; 15-minute lifetime; deep-linking left in the fog).

Sources are pinned where possible: MCP Python SDK tag `v2.3.0` (and `v1.30.0`), MCP spec repo commit `ff465f00`, HA Core tag `2026.10.1`, HA frontend `dev` at `736d1f4d` (2026-10-14), Supervisor `main` at `a2627a1c`, `home-assistant-js-websocket` tag `9.7.1`, Open WebUI tag `v0.12.2`. Web docs were read on 2026-10-14. ha-spark is cited at `96bbc22` (master).

## Answer

- **SDK v2 is stable and current; v1 is security-fix only, with no end date.** v2.0.0 shipped 2026-07-28 and v2.3.0 (2026-10-02) is the latest. Migrating ha-spark's server is small: a throwaway port changed about 15 lines in three files, and the full test suite plus `mypy --strict` passed on v2.3.0 (§1, §5).
- **URL elicitation comes from spec 2025-11-25. Under 2026-07-28 it rides multi round-trip requests (MRTR).** A v2 `@mcp.tool()` body can return the URL request directly. The spike ran that round trip against ha-spark's gated server (§2). On v1 the only route is the 2025-11-25 `-32042` error, and ha-spark's stateless server can't see whether the client supports it (§2.3).
- **No client that ha-spark documents today is confirmed to support URL elicitation:**
  - HA's MCP client declares no elicitation support.
  - Claude's hosted apps (claude.ai and Desktop connectors) don't document it.
  - Open WebUI's native MCP client handles URL mode only as a 2025-style server-pushed request, which ha-spark's stateless server can't send, and it doesn't handle `-32042`.
  - Claude Code is the one confirmed client: on 2026-07-28 connections it declares `elicitation.url`. It isn't in `DOCS.md`. (§3)
- **Ingress deep links work by path, not by hash.** `https://<HA>/app/<full-slug>/proposals/<id>` survives HA login, because the redirect keeps the path and query and drops the `#` part. The ingress session cookie is minted per panel load, so it doesn't need to survive. The panel's iframe always loads the bare ingress URL, though, so the app has to ask the parent page for the route over `postMessage`. Since HA 2026.10 the parent sends the right tail (§4).
- **Effort and risk:** the SDK migration is low effort, with medium dependency churn. The URL-elicitation feature is small *on top of* the #278 proposal store, which doesn't exist yet. Today's client reach is narrow: Claude Code only (§5).

## 2. URL elicitation

### 2.1 Spec revisions

- **Introduced in 2025-11-25:** "Added support for URL mode elicitation ([SEP-1036])" ([2025-11-25 changelog](https://github.com/modelcontextprotocol/modelcontextprotocol/blob/ff465f00f097901a6d1b662d57646767057feed3/docs/specification/2025-11-25/changelog.mdx#L17)). In that revision the server either sends `elicitation/create` with `mode: "url"` on a live session, or returns `URLElicitationRequiredError` (code `-32042`) whose elicitations "MUST be URL mode elicitations and have an `elicitationId`" ([2025-11-25 elicitation](https://github.com/modelcontextprotocol/modelcontextprotocol/blob/ff465f00f097901a6d1b662d57646767057feed3/docs/specification/2025-11-25/client/elicitation.mdx#L424-L456)). Clients declare `elicitation: {form, url}` "during initialization" (same file, L50-L75).
- **Reworked in 2026-07-28:** MRTR "replaces the previous approach of sending server-initiated requests". Servers return `InputRequiredResult` and clients retry with `inputResponses` ([2026-07-28 changelog item 7](https://github.com/modelcontextprotocol/modelcontextprotocol/blob/ff465f00f097901a6d1b662d57646767057feed3/docs/specification/2026-07-28/changelog.mdx#L24)). Item 11 removes `notifications/elicitation/complete` and `elicitationId`, and says the client "learns the outcome … by retrying the original request" (same file, L53-L60). Capabilities are declared "on each request" in `_meta` ([2026-07-28 elicitation](https://github.com/modelcontextprotocol/modelcontextprotocol/blob/ff465f00f097901a6d1b662d57646767057feed3/docs/specification/2026-07-28/client/elicitation.mdx#L49-L83)). The current page still carries "**New feature:** … Its design and implementation may change in future protocol revisions" (same file, URL-mode section).
- **Rules that bind ha-spark** (2026-07-28 elicitation, *Safe URL Handling* and *Security Considerations*):
  - "Servers **MUST NOT** send elicitation requests with modes that are not supported by the client."
  - "**MUST NOT** provide a URL which is pre-authenticated."
  - "**SHOULD** use HTTPS URLs for non-development environments."
  - "The MCP Server **MUST** verify the identity of the user who opens the URL."
  - `accept` "indicates that the user has consented to the interaction. It does not mean that the interaction is complete."
  - URL mode "**MUST NOT**" be relied on "to authorize users for themselves". ha-spark's approval rests on HA's ingress identity, not on the elicitation, so this is consistent with #268.

### 2.2 SDK v2 support

- **MRTR from a plain tool.** "At 2026-07-28 the server can no longer call the client, so tools return the question instead" ([v2.0.0 notes](https://github.com/modelcontextprotocol/python-sdk/releases/tag/v2.0.0)). "URL-mode elicitation rides this exact mechanism on a 2026 connection. The entry in `input_requests` is an `ElicitRequest` whose params are `ElicitRequestURLParams`" ([MRTR guide](https://github.com/modelcontextprotocol/python-sdk/blob/v2.3.0/docs/handlers/multi-round-trip.md#a-2026-07-28-result)).
  - The high-level `Elicit` resolver is form-only (`Elicit(message, Model)`) ([Dependencies](https://github.com/modelcontextprotocol/python-sdk/blob/v2.3.0/docs/handlers/dependencies.md)). URL mode is therefore built by hand.
  - An `@mcp.tool()` body may return `InputRequiredResult` as long as it uses no `Resolve(...)` parameters ([tools/base.py L91-L97, L181-L189](https://github.com/modelcontextprotocol/python-sdk/blob/v2.3.0/src/mcp/server/mcpserver/tools/base.py#L91-L97)).
  - The tool reads `ctx.protocol_version` and `ctx.client_capabilities` ([context.py L304-L333](https://github.com/modelcontextprotocol/python-sdk/blob/v2.3.0/src/mcp/server/mcpserver/context.py#L304-L333)).
- **Era check is mandatory.** "Return one from your handler on a `mode="legacy"` connection and … the client gets back a `-32603` 'Handler returned an invalid result' error. A server that serves both eras must check `ctx.protocol_version`" ([MRTR guide](https://github.com/modelcontextprotocol/python-sdk/blob/v2.3.0/docs/handlers/multi-round-trip.md#a-2026-07-28-result)). The spike reproduced exactly this (§5).
- **`requestState` sealing.** `MCPServer` "seals outgoing `requestState` and verifies every echo … under a key generated at process start". Each round is bound to a TTL (`RequestStateSecurity(ttl=...)`, "default 600 seconds"), to the originating request, and to the principal only when the SDK validated auth itself. With auth "terminated outside the SDK … this check is inert, unless `RequestStateSecurity(bind_principal=...)` supplies one" ([MRTR guide § Protecting `requestState`](https://github.com/modelcontextprotocol/python-sdk/blob/v2.3.0/docs/handlers/multi-round-trip.md#protecting-requeststate)). ha-spark terminates auth outside the SDK (`_token_gated`, ingress peer gate in [`api/server.py`](https://github.com/Kylevdm/ha-spark/blob/96bbc22/ha_spark/api/server.py)), so principal binding is inert by default. That is harmless under #268, because the retry only *reports* the proposal state and never commits. The 600 s round TTL is shorter than the 15-minute proposal lifetime, so a slow owner would see a rejected retry and a fresh flow. `ttl=900` would align them.
- **2025-era clients under v2:** `ctx.elicit_url()` is a server-to-client request. It raises `NoBackChannelError` on 2026 connections and also "on a legacy session against a `stateless_http=True` server". "`UrlElicitationRequiredError` from a tool is unaffected (it is an error response, not a request)" ([§ NoBackChannelError](https://github.com/modelcontextprotocol/python-sdk/blob/v2.3.0/docs/migration.md#server-initiated-sampling-elicitation-and-roots-raise-nobackchannelerror)).

### 2.3 What v1 (the current pin) can do

The premise that URL elicitation "needs `mcp>=2`" is only true of the MRTR form.

v1.30.0 already ships `UrlElicitationRequiredError` (`-32042`) ([exceptions.py L21](https://github.com/modelcontextprotocol/python-sdk/blob/v1.30.0/src/mcp/shared/exceptions.py#L21)), and FastMCP re-raises it as a protocol error ([tools/base.py L112](https://github.com/modelcontextprotocol/python-sdk/blob/v1.30.0/src/mcp/server/fastmcp/tools/base.py#L112)). The installed v1.30.0 speaks protocol 2025-11-25 at most.

ha-spark's server is stateless, though, so every request starts a session that is already "initialized" ([session.py L98](https://github.com/modelcontextprotocol/python-sdk/blob/v1.30.0/src/mcp/server/session.py#L98)) and has no client parameters. `check_client_capability` therefore returns `False` for everything ([L132-L135](https://github.com/modelcontextprotocol/python-sdk/blob/v1.30.0/src/mcp/server/session.py#L132-L135)). A stateless v1 server can't learn whether the client declared `elicitation.url`, and sending it anyway breaks the spec's MUST NOT. The alternative is stateful sessions, which v1.30 expires after 30 idle minutes ([v1.30.0 notes](https://github.com/modelcontextprotocol/python-sdk/releases/tag/v1.30.0)). That path also only reaches 2025-era clients that handle `-32042` or a pushed request. Inference: no v1 route is worth building for the clients in §3.

## 4. HA ingress deep links

**Panel URLs in HA 2026.10.** Core registers one generic `app` panel ([hassio `__init__.py` L354](https://github.com/home-assistant/core/blob/2026.10.1/homeassistant/components/hassio/__init__.py#L354)). It registers a dedicated panel at `/<addon-slug>` only when the add-on's sidebar panel is enabled ([addon_panel.py `_register_panel`](https://github.com/home-assistant/core/blob/1e76a638e0a73e689116e20452d803f74c9bf9c9/homeassistant/components/hassio/addon_panel.py#L106-L123)). `enable` is the Supervisor's `ingress_panel`, and `admin` is `panel_admin` ([Supervisor api/ingress.py L100-L111](https://github.com/home-assistant/supervisor/blob/a2627a1ce37032ecd5c6509813f70cf5b95d32c2/supervisor/api/ingress.py#L100-L111)). The frontend resolver has an `app` panel and no `hassio` panel ([partial-panel-resolver.ts](https://github.com/home-assistant/frontend/blob/736d1f4dec41856791039803159fa5795721aea1/src/layouts/partial-panel-resolver.ts)). I found no redirect from the old `/hassio/ingress/<slug>` form, so verify that on a live instance before relying on it. The stable link is **`/app/<full-slug>/…`**. A repository add-on's full slug carries a repository prefix in front of `ha_spark_addon` ([config.yaml](https://github.com/Kylevdm/ha-spark/blob/96bbc22/ha_spark_addon/config.yaml)), so ha-spark has to learn its own slug at runtime.

**The hash route doesn't reach the iframe.** The app panel renders `<iframe src=${this._addon.ingress_url}>`, the bare ingress URL, whatever the outer URL holds ([ha-panel-app.ts L141-L152](https://github.com/home-assistant/frontend/blob/736d1f4dec41856791039803159fa5795721aea1/src/panels/app/ha-panel-app.ts#L141-L152)). A `#/proposals/<id>` on the HA URL is therefore not forwarded.

**The path tail does reach it, over `postMessage`.** An embedded app sends `home-assistant/subscribe-properties`. The parent then posts `home-assistant/properties` with `route` (the route tail after `/app/<slug>`), re-sends it on route changes, and accepts `home-assistant/navigate` back ([ha-panel-app.ts L411-L483](https://github.com/home-assistant/frontend/blob/736d1f4dec41856791039803159fa5795721aea1/src/panels/app/ha-panel-app.ts#L411-L483)). A bug that put the wrong tail in the route for apps opened from their dedicated sidebar panel was fixed in [frontend PR #54404](https://github.com/home-assistant/frontend/pull/54404) (merged 2026-09-27). That fix is in frontend `20260930.0`, which HA `2026.10.0` ships (`home-assistant-frontend==20260930.2`, [manifest](https://github.com/home-assistant/core/blob/2026.10.0/homeassistant/components/frontend/manifest.json)). The generic `/app/<slug>` tail was computed correctly before that fix. Inference: ha-spark's hash-routed ingress app ([#254](https://github.com/Kylevdm/ha-spark/issues/254#issuecomment-6111055783)) can subscribe on load and map a `route.path` of `/proposals/<id>` onto its own hash route. It must check that `event.source` is `window.parent` and treat the route as an untrusted hint. The approval itself still needs the owner's click and the digest check (#268).

**It survives HA login (path and query only).** When unauthenticated, the frontend's `getAuth` sends the browser to `/auth/authorize` with `redirect_uri` built by `genRedirectUrl()`, whose comment reads "Get current url but without # part", from `protocol//host + pathname + search` ([home-assistant-js-websocket 9.7.1 auth.ts L61-L65](https://github.com/home-assistant/home-assistant-js-websocket/blob/9.7.1/lib/auth.ts#L61-L65)). The frontend uses that default ([core.ts](https://github.com/home-assistant/frontend/blob/736d1f4dec41856791039803159fa5795721aea1/src/entrypoints/core.ts), `getAuth({ hassUrl, … })`, js-websocket `9.7.1` per [package.json](https://github.com/home-assistant/frontend/blob/736d1f4dec41856791039803159fa5795721aea1/package.json)). So `/app/<slug>/proposals/<id>` comes back intact after login, and `#…` would be lost. This is another reason to use the path. The companion apps' external-auth path wasn't checked.

**The ingress session token doesn't need to survive.** Each app-panel load calls `createHassioSession`, which posts `/ingress/session` and sets the `ingress_session` cookie with `path=/api/hassio_ingress/;SameSite=Strict` ([ingress.ts](https://github.com/home-assistant/frontend/blob/736d1f4dec41856791039803159fa5795721aea1/src/data/hassio/ingress.ts)). The panel re-validates every 60 s and mints a new session on failure ([ha-panel-app.ts L333-L340](https://github.com/home-assistant/frontend/blob/736d1f4dec41856791039803159fa5795721aea1/src/panels/app/ha-panel-app.ts#L333-L340)). The Supervisor holds sessions for 15 minutes, sliding on each request ([supervisor/ingress.py L134-L171](https://github.com/home-assistant/supervisor/blob/a2627a1ce37032ecd5c6509813f70cf5b95d32c2/supervisor/ingress.py#L134-L171)). It rejects requests without a valid cookie (`HTTPUnauthorized`) and denies non-admins when `panel_admin` is set ([api/ingress.py L144-L166](https://github.com/home-assistant/supervisor/blob/a2627a1ce37032ecd5c6509813f70cf5b95d32c2/supervisor/api/ingress.py#L144-L166)). A link must therefore target the **HA frontend URL**, never the raw `/api/hassio_ingress/<token>/…` URL, which 401s in a fresh tab. A frontend URL that only routes after HA authentication also meets the spec's "MUST NOT … pre-authenticated" rule.

**Building the absolute URL.** The elicitation URL needs HA's own base URL: `external_url`, or `internal_url` on the LAN, which [#268 §5](https://github.com/Kylevdm/ha-spark/blob/research/268-agent-config-approval/docs/research/268-agent-config-approval.md) located in HA's `/api/config`. The spec wants HTTPS outside development (§2.1). Many households will have an `http://` LAN base or no `external_url` at all, so the server must omit the elicitation when the base is missing, and the plain result still works. The HA "My" redirect service has `supervisor_app` only for the app's *info* page, not for ingress with a sub-path ([ha-panel-my.ts](https://github.com/home-assistant/frontend/blob/736d1f4dec41856791039803159fa5795721aea1/src/panels/my/ha-panel-my.ts)).

## 5. Effort and risk

**Spike (throwaway, not committed).** I copied ha-spark `96bbc22` into a scratch directory with `mcp==2.3.0` installed. The rest of ha-spark's pins resolved cleanly: `fastapi 0.143.1`, `starlette 1.8.0`, `pydantic 2.14.1`, `httpx 0.28.1` alongside `httpx2 2.13.1`, `sse-starlette 3.5.0`, `opentelemetry-api 1.45.1`. The port touched:

- `mcp_server.py`: imports, base class, the `call_tool` signature and the constructor arguments.
- `api/server.py`: transport arguments moved to `streamable_http_app(...)`.
- `test_agent_mcp.py`: one import.

Results:

- `pytest`: 1201 passed and 1 skipped. The one failure, `test_solis_export.py::test_misread_discharge_half_is_not_kept`, also fails on unmodified master under v1.30.0, so it predates the port and is unrelated.
- `mypy --strict ha_spark`: clean.
- A probe tool on the gated server returned an `InputRequiredResult` URL elicitation. A v2 `Client` with an elicitation callback negotiated `2026-07-28` and reported `elicitation.url`. It received the URL and retried with the sealed state echoed, and the tool then reported the outcome. A read-tier denial of `set_config` still came back as `Unknown tool`.
- The same probe on a `mode="legacy"` connection failed with `-32603`, which confirms the era check is required.

| Item | Effort | Risk |
|---|---|---|
| SDK v1 → v2 migration | **Small.** About 15 lines in three files, plus the pin and `DOCS.md`/CHANGELOG | **Medium.** Five new or replaced transitive packages need the CLAUDE.md justification. Pin tightly: v2.3.0 put "Behaviour changes" in a minor release, and v2 is about 11 weeks old. `mcp-types` is lockstep-pinned by `mcp` itself |
| URL elicitation on `set_config` | **Small, but blocked.** Era check, `elicitation.url` capability check, base-URL/slug/route assembly, `ttl=900`. It depends on the #278 proposal store and the `get_config_proposal` tool, which aren't built yet | **Low** for safety: the retry only reports and never commits (#268). The risk is in the URL: it must not be pre-authenticated, HTTPS isn't guaranteed, and the slug is learned at runtime |
| Ingress deep-link route | **Small.** The app subscribes to `home-assistant/properties` and maps `route.path` | **Low to medium.** Relies on frontend behaviour that's undocumented outside the source and was fixed in HA 2026.10, so older HA cores mis-split the dedicated-panel path |
| Client reach | n/a | **High uncertainty.** Of the documented clients, none is confirmed. Claude Code is the only confirmed consumer. HA's client can't elicit at all |
| Staying on v1 | none | **Low near-term.** Security fixes continue with no published end date. Long-term drift: 2026-07-28 clients fall back to the 2025 handshake |

## Recommendation (for the map to decide)

The approval hand-off doesn't need SDK v2 to be safe or usable. #268's propose-only contract and #278's ingress approval work on v1 for every client. URL elicitation only adds a "click here" for 2026-07-28 clients, and today that means Claude Code.

That suggests decoupling:

1. Ship the proposal store and ingress approval in v1.0.0 on the current pin. Also ship the path-based deep link, as a URL the tool result *prints*, `…/app/<slug>/proposals/<id>`. That is useful in every client and needs no SDK change.
2. Treat the SDK v2 migration as its own small phase, either in or after v1.0.0, justified by v1's maintenance status rather than by elicitation.
3. Add URL elicitation once v2 is in and a targeted client, ideally a hosted Claude app, is confirmed to declare `elicitation.url`.

If the map wants it all in v1.0.0, the spike shows it's feasible at small cost. The risk lies in dependency churn and narrow reach, not in the security model.
