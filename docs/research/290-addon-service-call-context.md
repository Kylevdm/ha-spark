# Add-on service-call context through the Supervisor proxy

Research for [“Research: which HA user context do add-on service calls carry?”](https://github.com/Kylevdm/ha-spark/issues/290). Source revisions inspected: [Core `a85fd94`](https://github.com/home-assistant/core/tree/a85fd94211ac3822ace9d515cf52adb3fd7b66fe) and [Supervisor `fd35f22`](https://github.com/home-assistant/supervisor/tree/fd35f22fe930a1177a97d1f8fe1e3030fcb43391). The answer below describes those revisions; it is not a runtime test of a particular installation.

## Answer

For the current Unix-socket transport, an add-on service call through either Supervisor's REST or WebSocket proxy reaches Core with **the Supervisor system user's ID** in `call.context.user_id`. The account's current display name is **“Supervisor”**, not “hassio”; the `hassio` integration creates or recovers that account and stores it in `hass.data[DATA_SUPERVISOR_USER]`. Its ID is installation-specific and must not be hard-coded. [Core user creation and recovery](https://github.com/home-assistant/core/blob/a85fd94211ac3822ace9d515cf52adb3fd7b66fe/homeassistant/components/hassio/__init__.py#L177-L222), [Core data assignment](https://github.com/home-assistant/core/blob/a85fd94211ac3822ace9d515cf52adb3fd7b66fe/homeassistant/components/hassio/__init__.py#L339-L347), [data key](https://github.com/home-assistant/core/blob/a85fd94211ac3822ace9d515cf52adb3fd7b66fe/homeassistant/components/http/const.py#L20-L24), [display name](https://github.com/home-assistant/core/blob/a85fd94211ac3822ace9d515cf52adb3fd7b66fe/homeassistant/const.py#L1050).

An integration can compare `call.context.user_id` with `hass.data[DATA_SUPERVISOR_USER].id` after `hassio` has set up. The `hassio` config entry also persists the ID under `ENTRY_DATA_USER`, but the in-memory user is the exact object Core's socket authenticator uses. If the user is absent, fail closed rather than guessing by name. [Core user storage](https://github.com/home-assistant/core/blob/a85fd94211ac3822ace9d515cf52adb3fd7b66fe/homeassistant/components/hassio/__init__.py#L183-L213), [Core socket authentication](https://github.com/home-assistant/core/blob/a85fd94211ac3822ace9d515cf52adb3fd7b66fe/homeassistant/components/http/auth.py#L190-L213), [entry key](https://github.com/home-assistant/core/blob/a85fd94211ac3822ace9d515cf52adb3fd7b66fe/homeassistant/components/hassio/const.py#L154-L157).

## Why both proxy paths have that context

Supervisor checks an add-on's `SUPERVISOR_TOKEN` against its add-on registry and checks `access_homeassistant_api`. It then creates its **own** Core request, forwarding a small header allowlist and the request body. The allowlist does not include a caller identity or authorization header. For WebSockets, Supervisor authenticates the add-on, opens its own Core WebSocket, and relays allowed commands on that connection. Thus Core receives Supervisor's identity, not the add-on's slug or token. Every add-on permitted to use these proxy paths shares that Core user ID. [REST proxy](https://github.com/home-assistant/supervisor/blob/fd35f22fe930a1177a97d1f8fe1e3030fcb43391/supervisor/api/proxy.py#L28-L36), [REST token check and forwarding](https://github.com/home-assistant/supervisor/blob/fd35f22fe930a1177a97d1f8fe1e3030fcb43391/supervisor/api/proxy.py#L111-L149), [WebSocket auth and upstream connection](https://github.com/home-assistant/supervisor/blob/fd35f22fe930a1177a97d1f8fe1e3030fcb43391/supervisor/api/proxy.py#L345-L396), [message relay](https://github.com/home-assistant/supervisor/blob/fd35f22fe930a1177a97d1f8fe1e3030fcb43391/supervisor/api/proxy.py#L285-L313).

Supervisor currently prefers a dedicated Unix socket when the Core container supports and is configured for it. Core authenticates every request on that socket as `DATA_SUPERVISOR_USER`; its WebSocket auth phase uses that authenticated request user. A REST service view builds `Context(user_id=user.id)` from the request, and the WebSocket `call_service` handler builds context from its connection user. Both pass that context to `hass.services.async_call`. [Supervisor transport selection](https://github.com/home-assistant/supervisor/blob/fd35f22fe930a1177a97d1f8fe1e3030fcb43391/supervisor/homeassistant/api.py#L70-L140), [Core socket authentication](https://github.com/home-assistant/core/blob/a85fd94211ac3822ace9d515cf52adb3fd7b66fe/homeassistant/components/http/auth.py#L190-L224), [Core REST context](https://github.com/home-assistant/core/blob/a85fd94211ac3822ace9d515cf52adb3fd7b66fe/homeassistant/helpers/http.py#L126-L140), [REST service call](https://github.com/home-assistant/core/blob/a85fd94211ac3822ace9d515cf52adb3fd7b66fe/homeassistant/components/api/__init__.py#L390-L453), [WebSocket socket auth](https://github.com/home-assistant/core/blob/a85fd94211ac3822ace9d515cf52adb3fd7b66fe/homeassistant/components/websocket_api/auth.py#L71-L83), [WebSocket context and call](https://github.com/home-assistant/core/blob/a85fd94211ac3822ace9d515cf52adb3fd7b66fe/homeassistant/components/websocket_api/connection.py#L109-L111), [WebSocket service call](https://github.com/home-assistant/core/blob/a85fd94211ac3822ace9d515cf52adb3fd7b66fe/homeassistant/components/websocket_api/commands.py#L315-L341).

Supervisor also has a TCP fallback for an older or not-yet-socket-configured Core container. It obtains a Core access token using its stored refresh token; Core's normal bearer-token authenticator associates a request with that token's user. This path is therefore dependent on the token owner's identity and is not proven by the Unix-socket code alone. The current `hassio` setup removes the Supervisor user's refresh tokens after switching to the dedicated socket. Confirm the actual transport and user on installations where this fallback matters. [Supervisor fallback](https://github.com/home-assistant/supervisor/blob/fd35f22fe930a1177a97d1f8fe1e3030fcb43391/supervisor/homeassistant/api.py#L160-L205), [Supervisor REST and WebSocket auth](https://github.com/home-assistant/supervisor/blob/fd35f22fe930a1177a97d1f8fe1e3030fcb43391/supervisor/homeassistant/api.py#L221-L245), [Core bearer-token user](https://github.com/home-assistant/core/blob/a85fd94211ac3822ace9d515cf52adb3fd7b66fe/homeassistant/components/http/auth.py#L128-L151), [refresh-token removal](https://github.com/home-assistant/core/blob/a85fd94211ac3822ace9d515cf52adb3fd7b66fe/homeassistant/components/hassio/__init__.py#L430-L433).

## What else can have the same context?

- A normal user's REST call, WebSocket call, or long-lived token resolves to **that token's user**, not the Supervisor user. Other system users have their own IDs. This distinguishes their direct service calls by user ID, provided their credentials have not been shared. [Core bearer-token authentication](https://github.com/home-assistant/core/blob/a85fd94211ac3822ace9d515cf52adb3fd7b66fe/homeassistant/components/http/auth.py#L128-L151), [Core REST context](https://github.com/home-assistant/core/blob/a85fd94211ac3822ace9d515cf52adb3fd7b66fe/homeassistant/helpers/http.py#L136-L140), [Core WebSocket context](https://github.com/home-assistant/core/blob/a85fd94211ac3822ace9d515cf52adb3fd7b66fe/homeassistant/components/websocket_api/connection.py#L109-L111).
- An automation creates a new `Context(parent_id=...)` on trigger, so its action's direct service calls normally have no `user_id` even when the triggering call had one. A script is different: its service handler passes `service.context` into the script, and its service actions pass that same context to `hass.services.async_call`. A script started by Supervisor can therefore produce a later command with the **same Supervisor user ID and context**. [Automation trigger context](https://github.com/home-assistant/core/blob/a85fd94211ac3822ace9d515cf52adb3fd7b66fe/homeassistant/components/automation/entity.py#L461-L486), [script service context](https://github.com/home-assistant/core/blob/a85fd94211ac3822ace9d515cf52adb3fd7b66fe/homeassistant/components/script/__init__.py#L750-L764), [script action service call](https://github.com/home-assistant/core/blob/a85fd94211ac3822ace9d515cf52adb3fd7b66fe/homeassistant/helpers/script.py#L1079-L1094).
- Assist/conversation takes its REST, WebSocket, or `conversation.process` service caller's context. Thus ordinary Assist use does not become the Supervisor user, but conversation processing **initiated by Supervisor** can carry its context downstream. [conversation REST and WebSocket](https://github.com/home-assistant/core/blob/a85fd94211ac3822ace9d515cf52adb3fd7b66fe/homeassistant/components/conversation/http.py#L58-L66), [conversation REST view](https://github.com/home-assistant/core/blob/a85fd94211ac3822ace9d515cf52adb3fd7b66fe/homeassistant/components/conversation/http.py#L255-L269), [conversation service](https://github.com/home-assistant/core/blob/a85fd94211ac3822ace9d515cf52adb3fd7b66fe/homeassistant/components/conversation/services.py#L48-L62).

## Consequence for ADR-0008

The ADR's **identity expectation is true for current Unix-socket proxy calls**, but its stronger implication that `call.context.user_id` identifies *ha-spark's add-on* is false. It identifies the shared Supervisor principal; other permitted add-ons have it too, and scripts can inherit it. Session ID and authority epoch establish freshness and reject stale commands, but they do not establish which add-on sent a command. This is an inference from the proxy's authentication and identity replacement plus Core's context propagation cited above.

For a service command that must be specific to ha-spark's add-on, require an additional unguessable add-on credential or a request authenticator derived from one, provisioned privately between the integration and add-on. Verify it in the integration alongside the Supervisor user ID, session ID, and authority epoch; rotate and revoke it with the add-on session. The service payload passes through the REST proxy, and the WebSocket proxy forwards `service_data`, so this can be built at the application layer. This is a design recommendation inferred from those source paths, **not** a built-in Home Assistant add-on identity signal. [REST body forwarding](https://github.com/home-assistant/supervisor/blob/fd35f22fe930a1177a97d1f8fe1e3030fcb43391/supervisor/api/proxy.py#L130-L149), [WebSocket service data](https://github.com/home-assistant/core/blob/a85fd94211ac3822ace9d515cf52adb3fd7b66fe/homeassistant/components/websocket_api/commands.py#L325-L340).
