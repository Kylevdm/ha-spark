Problem. One Hold requires the scheduler and Solis module to reconstruct durable ownership, confirmation, clearance and refusal episodes independently.

Direction. Concentrate durable Hold transitions and persistence/read-back ordering in a deep module; retain the Solis adapter and execution gate.

Evidence. The open #446 follow-up identifies two places that can adopt an owner’s manual Off after restart. #448 adds release backoff to this same lifecycle. Centralising ownership reduces duplicated reasoning; it cannot resolve ambiguous hardware evidence by itself.

Deletion test. Deleting a shallow boolean helper only moves code. Absorbing record reconstruction and ordering adds depth: deleting the deep module would spread those invariants back across startup, minute passes and handover.

Test surface. Existing durable-hold and verified-release tests already cover overlapping causes, save-before-write, stale evidence and read-back. Exercise these sequences through the lifecycle interface with a controllable adapter; keep real Solis read-back tests.

  • locality: one Hold lifecycle
  • leverage: startup, ticks, handover
  • interface tests span restart
ADR-0007 preserved. Phase 2 remains add-on-owned. Settle #446’s evidence policy separately; do not disguise a behaviour change as extraction.

Problem. The daemon owns evidence deduplication, task admission, daily evaluation and cancellation while a different module holds process-global retry times.

Direction. Deepen the Readiness signal module around evidence lifecycle and task lifetime, preserving pure replay and evaluation as internal seams.

Evidence. test_readiness_scheduler.py:23 starts the daemon and patches planning, SoC, learning, capture and evaluation to prove a blocked recorder cannot delay protection. This is the trigger anticipated in docs/fog.md:113, now exercised by #431–435.

Deletion test. Moving the closure into another file is shallow. The module earns depth only if its interface hides retry, deduplication and cleanup knowledge currently scattered across the daemon and globals.

Test surface. Keep the blocked-recorder daemon test as an integration guarantee. Test lifecycle timing, failed evidence collection and cancellation at the same seam callers use. Reuse the HA and SQLite adapter implementations; no generic job framework.

  • locality: evidence lifecycle together
  • leverage: fewer daemon fixtures
  • interface tests cover task lifetime
Readiness remains a recommendation, never an authority gate. Preserve guard-before-recording order, missing-data provenance and durable notice deduplication.

Problem. The ingress AppState module owns config validation, fallback policy, persistence and fencing, while the daemon separately owns invalidation.

Direction. Use phase 3’s deep Settings module to own the accepted revision, commit outcome and active snapshot; ingress and CLI become adapters at its seam.

Evidence. Fault injection reproduced a reported save failure with live min_soc=20 and persisted min_soc=30: replace happens before reload. Existing test_api.py:456 checks secret-safe failure and live state, but not disk. Spec #456 already requires atomic revision tests and this module.

Deletion test. Removing AppState policy would currently spread it into callers. Moving that policy into the planned module creates depth; adding a forwarding settings class without owning commits would remain shallow.

Test surface. Use the planned Settings interface on temporary files: commit faults, revision conflict, byte-identical rejection, snapshot and fence outcomes. Keep adapter tests for ingress authentication and CLI transport. One filesystem adapter is sufficient.

  • locality: commit and snapshot together
  • leverage: ingress, CLI, import
  • interface tests cover atomicity
Align with ADR-0006 and spec #456. The injected reload failure demonstrates error-path inconsistency, not a claim that ordinary successful saves split state.

Problem. Fallback application, authority mirroring, recovered-plan verification and retry timing are coordinated across helper functions and the main loop.

Direction. Deepen fallback lifecycle orchestration while preserving the SoC monitor’s evidence judgment and the Authority store’s durable authority.

Evidence. A failed recovered plan must reapply fallback on the same tick; recovery then waits five minutes while unconfirmed fallback retries each minute. That ordering is spread across scheduler helpers and loop-local state.

Deletion test. A shared apply helper removes duplication but adds little depth. The module must hide the ordering-sensitive recovery protocol and retry state behind its interface to earn leverage.

Test surface. Existing test_scheduler.py:5818, 5949 and 6012 cover same-tick reapply, retry cadence and authority refusal. Move detailed sequences to the lifecycle seam with clock and device adapter control; retain daemon integration checks.

  • locality: recovery protocol together
  • leverage: one retry implementation
  • interface tests span partial failure
Preserve typed verification and authority-save failure behaviour. Do not merge SoC evidence with authority or add future liveness fallback causes during this refactor.

Direction. Give the existing forecast history module depth over read-only evidence access, legacy handling and record decoding.

Evidence. load_readiness checks sqlite_master and PRAGMA columns, selects forecasts and constructs ForecastHistoryRecord itself. ForecastLedger already decodes history; callers now share schema knowledge.

Deletion test. Another forwarding helper is shallow. Moving real SQL, compatibility and decoding into the existing module concentrates complexity; deleting it would redistribute that knowledge to callers.

Test surface. Preserve the legacy-database read-without-mutation test at the history interface. Test absent evidence and current revisions with actual temporary SQLite databases; a second storage adapter is hypothetical.

  • locality: schema knowledge together
  • leverage: shared history interpretation
  • interface reads cannot migrate
Keep absent or legacy evidence absent. No fabricated forecasts, storage framework or schema redesign is needed.

Keep the depth already earned

current_plan centralises input gathering, tariff construction and planning. Its short implementation is not a reason to delete it: that would spread ordering knowledge back across callers.

ExecutionContext and BusCoordinator already hide authority fencing and serialised device actions. Preserve this seam. Keep pure compute_plan, replay_day and evaluate_readiness tests; preserve ADR-0002’s auditable reservations.

Do not revive the old broad “split scheduler” proposal or generalise device support ahead of phase 4/8. The useful extraction follows a lifecycle, not file length.
